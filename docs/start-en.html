Start with “Can my Raspberry Pi do this?”

Start with a suitable part using your Raspberry Pi, Mac or Linux machine. This guide helps you work with AI to assess the environment, build something small, check it and continue. Owning our complete R6S, Pi 5 and two-Mac setup is not a prerequisite.

The first milestone is a receive/transmit display using synthetic data that passes shared checks. Then investigate whether corresponding counters can be read on your device. Installing OpenWrt is a separate, later stage.

What “AI-assisted concept distribution” means

Here, “concept distribution” means sharing goals, design reasoning, component roles, inputs/outputs and checks so that a reader can implement them with AI. It is our term for this approach, not an existing standard or a claim that AI can reproduce everything from prose.

SharedChosen locally
Meaning of observations and countsDevice, OS, interface and observation coverage
Data format, calculations, failure states and checksLanguage, UI, storage and sampling interval
How to record decisions and validationSoftware versions, selected functions and operation

The unit of reproduction differs from distributing identical finished software. Different code and screens can still be compared against a shared contract. Passing this introductory contract does not establish equivalence to our complete dashboard, AI review system or NPU experiment.

Publishing every source file on GitHub is not a prerequisite. We share the required design information and test data here, linking to existing public code where an exact driver or implementation version matters. Licenses and redistribution conditions for each OSS component or SDK still apply.

Adapt the plan to the equipment

  • Check model, memory, CPU architecture, OS/kernel, available storage, media and existing services. A model name alone is insufficient.
  • Establish which machine the AI can access. Without read permission, ask the reader for only the necessary facts and keep unknowns explicit.
  • Counters on an ordinary LAN endpoint describe that interface, not automatically all household traffic. Check routing or mirror-port observation positions and potential double counting separately.
  • Select software using current official device/OS/version documentation. This experiment’s dated configuration is not a permanent recommendation for the latest version.

Plan storage allocation before extending the experiment

A large allocation is not a prerequisite for the first small synthetic-data exercise. If you intend to add software, traffic analysis or NPU experiments, discuss a larger initial system allocation with AI before installing the OS, allowing room for future additions and update workspace.

Budget separately for writable OS/application space and the destination for logs/databases; total free media capacity alone is insufficient. When reusing an existing environment, first inspect its layout and assess whether it already has enough room. Basic functionality may fit a smaller layout.

In this experiment, expanding p2 from 256MiB to 5GiB required backing up/restoring data and checking boot. The 5GiB allocation is our choice; your equipment may need a different layout or capacity.

Restore logs together with “how far they were read”

On October 23, 2026, Snort log collection temporarily stopped after data restoration during partition expansion. The bytes were restored, but the file identity (inode) changed and no longer matched the collector’s saved file and read position. The collector stopped on that mismatch; it did not establish that the data was lost.

  • Before restore: preserve logs, databases and cursor/checkpoint as a consistent set. Record software versions and the log generation already processed.
  • After restore: verify content against the backup and an unambiguous match for the committed range. A filename, modification time or inode alone is insufficient to identify the same log.
  • On a mismatch, pause collection for investigation and preserve history and position. Do not automatically disable identity checks, clear the cursor or jump to the beginning/end: these can duplicate or skip records.

In this case, the owner verified backup contents and the committed range, migrated identity once while preserving position, then confirmed normal incremental collection, DB consistency and the UI. This was accepted for that software/state combination, not prescribed for every environment. Ask AI to include before/after reconciliation and collection-resumption checks in the plan.

A production log cursor is separate from the rate-counter reset in the introductory contract below. Its fresh-baseline rule must not be applied to resetting an audit-log cursor.

After a successful build, verify compatibility and recovery

A successful build establishes that an artifact was generated. Booting and networking on the current device, and being able to recover after failure, require separate checks. These checks accounted for a substantial part of the October 29 R6S kernel repair.

  • Compatibility: what it must work with — Reconcile actual configuration, kernel ABI, existing modules/drivers and required services, beyond device names or version strings. Bind generated artifacts to running content using hashes or Build IDs. Identical version strings need not mean identical repairs.
  • Recovery: what to restore, where and how — Preserve boot content, configuration and data matching the current version. Backup receipt or hash agreement alone does not establish restorability. Check actual rescue-media boot, management access independent of the affected route, recovery-artifact transfer, and the target partition/procedure. Record separately whether an actual restoration was exercised.
  • After application: separate writing, activation and recovery — A completed write can leave the old kernel running until reboot. After booting the new content, check connectivity, DNS, data and required processing. Our NPU first recovered after a manual driver load. A later startup-order repair was verified by scoring resumption without manual intervention after a normal reboot that afternoon. Manual and automatic recovery were checked separately.

Ask AI to separate pre-application checks, post-application checks and unknowns in the plan. Defer the change until its prerequisites are established; a kernel change is not required for the introductory counter-display experiment.

Verify automatic startup from prerequisites through real output

“It works now” and “it returns automatically after reboot” require different checks. On this R6S, an enabled service did not load its NPU driver, so inference failed after reboot. On October 29, the startup order was repaired and actual scoring resumed after a normal router reboot without manual intervention.

  • List prerequisites: storage, compatible drivers, devices and configuration. Bound readiness waits and record failure reasons instead of waiting forever or showing zero after failure.
  • Record what worked without manual help: distinguish enablement, manual start, service restart, normal router reboot and power-off/on boot. Perform only the interruptions and restarts authorized by the owner.
  • Check real output: beyond process existence, verify observations, scores and persistence in the new boot generation, with gaps and failures kept distinct from normal results. One successful normal reboot is not a power-cycle test or long-term stability proof.
  • Carry the complete set forward: manage the startup script with its compatible driver, libraries, configuration and dependencies. Revalidate the next build and do not assume retained rescue media were updated alongside it.

A small shared contract: receive/transmit counters

The first contract is interface-counter-v1, newly defined for this introductory guide. It is not the API of our deployed review system.

  • Input is previous/current for the same interface. Each has elapsed_ms (monotonic elapsed milliseconds), rx_bytes and tx_bytes (nonnegative integer cumulative bytes). null means no sample. Changing interface discards the old baseline.
  • Decision order: null current → unavailable; validate existing sample fields for type, finiteness and nonnegative integers → invalid if malformed; null previous → warming_up; elapsed difference ≤ 0 → invalid; either counter decreased → reset; otherwise ok.
  • Only for ok, calculate bytes/s in each direction as (current counter − previous counter) / (elapsed millisecond difference / 1000). Distinguish bytes from bits; round for display only.
  • For every non-ok state both rates are null. Do not display failures, reset or invalid as zero or “safe.” Establish a fresh baseline at startup, after failure and after reset; do not average across missing data. Discard invalid samples and clear the baseline.
  • Let the reader choose collection interval; visibly mark overdue data as stale or awaiting update. If an implementation cannot preserve cumulative integer precision, declare its supported range rather than silently rounding.

Check dependencies and service ownership as a coherent set

For execution-engine/shared-library changes, qualify update/recovery combinations across consumers and packages with exact-version pins. When stopping services, inspect ownership of processes and children rather than relying only on executable names; align the selected services with termination checks.

Network-service stops can interrupt traffic without a host reboot. Verify dependent detection/scoring and readers on other machines follow the new runtime generation. Preserve aborted and successful attempts with their separate interruption measurements rather than overwriting failures with later success.

Verify actual consumers through final persistence and publication

For shared-library updates, verify consumers load the new object beyond checking the package version. AI work can fail during later history reading/publication even after responses validate. Retain exclusion guards, align the relevant reads with bounded waiting and verify persistence/publication in the next actual scheduled run.

When moving from comparison models to one operational model, retain old models/history/observation baselines and reconcile resource release with new-reader acceptance. Installing diagnostics and obtaining useful evidence at a natural event are separate outcomes. Do not synthesize diagnostics for past events; record the generation from which capture becomes available.

Verify recovery and retain evidence for diagnosis

After recovery, check log reception, hourly processing and notification delivery separately from connectivity and dashboard access. Consider readiness/retry handling within existing service management for jobs that can start too early. Configuration validation/manual recovery does not establish automatic recovery after the next power loss. Do not subtract counters across observation generations to claim zero loss.

A high anomaly score may be impossible to attribute from aggregates alone. Design bounded retained context with explicit scope, retention and private fields. Separate score measurement, traffic attribution and normal/malicious classification. The diagnostic feature itself also needs independent review and executable/input-order verification.

Verify normal recovery and adoption by running processes

For recovery materials, distinguish a standalone package signature from authentication through a signed repository index. Verify that the original version can be authenticated and restored through the package manager’s normal path in isolation. Missing standalone signatures alone do not establish failed recovery; bypassing checks or adding trust keys is not a substitute. Record source rebuilds separately from adoption of official prebuilt binaries.

After a library update, verify that its consumers actually load the new executable/library, beyond checking the installed package version. Separate service-recovery time, management-path gaps and ordinary-network outages, stating sampling intervals and scope. For schedule changes, distinguish configuration readback, tests and the next natural execution; manual catch-up must not become an on-time success in history.

Verify notification arrival and review execution separately

When adding notifications, verify decision rules, provider acceptance, actual device arrival, on-screen display and icon badges separately. Decide whether the badge represents unread items or current warnings, and never convert stale/unknown state to zero. Check registration after a service migration and limit send tests to devices and counts chosen by the owner. When zero warnings should clear the badge, allow a retry if clearing failed and the same state arrives again.

Scheduled review also separates configuration, actual start, complete validated responses, persistence/publication and the next natural occurrence. Successful manual catch-up neither rewrites a missed occurrence as successful nor establishes that recurrence was repaired.
