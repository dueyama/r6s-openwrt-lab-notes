Updates and recovery

How OS updates preserve custom functions, configuration and history.

Page revision: 2026-11-27 · Dates and acceptance scopes for updates, reviews and recovery

What you can explore here

A router needs to keep working after updates, with its settings and history available. This page brings together the approach to following OpenWrt upstream while keeping custom functions, and the checks used for updates, backups and recovery.

The basic idea is to connect each software change with what was verified on the device: boot, connectivity, data and monitoring functions.

Terminology
Upstream / stable branch
Upstream is the original project. A stable branch is the selected stable release line.
ABI / backport
An ABI defines binary compatibility. A backport applies a fix from a newer line to an older one.
APK / persistence
APK here is an OpenWrt software-package format. Persistence retains configuration and history across reboot or update.
SQM / CAKE
Queue-management and traffic-shaping mechanisms used to limit delays under congestion.
PWA / Web Push
PWA features support app-like use of a web UI. Notification delivery moved from OneSignal to standard Web Push on November 13, 2026.
DNS / SSD
DNS resolves names to network addresses. An SSD stores backups.
Receipt (verification record)
A record binding the target version, evidence and result; its existence alone does not establish adoption or completion of every stage.
Formal finish (workflow acceptance)
Workflow completion after required originals, API and display evidence; distinct from fixing every software issue.
Projection / rebinding
Projection turns stored logs into aggregate/display data. Rebinding ties a review result to evidence for the corresponding configuration/version.

CVE-2026-98432: freeing memory while another reader still uses it

During IPv4 TCP connection setup, IP options are handed from the request socket to a child socket. Destroying the child can free those options while another CPU builds a SYN response: a use-after-free. Readers already use RCU protection, but ordinary kfree() does not wait for them.

The repair changes frees in inet_sock_destruct() and tcp_v4_reqsk_destructor() to kfree_rcu(), deferring reclamation until an RCU grace period ends. It also covers shared options during request-socket migration. This aligns object lifetime with reader protection; it does not establish IPv6-wide verification.

Boot media and persistence
Official OpenWrt was first tested from SD. The working SD card was kept for recovery before regular operation moved to eMMC. Normal operation boots from eMMC with the SD removed; when needed, the device is shut down and the saved SD inserted so it can boot from SD with priority. On 2026-09-25, an eMMC → saved SD → eMMC round trip was verified. Configuration, operational SQLite and monitoring history are retained separately. Update correspondence
Source commits, build configuration, signed packages, image hashes and installation results are mapped together. Configuration and consistent DB backups are retained before updates; configuration continuity, DB integrity, connectivity, Snort and UI behavior are checked afterward. Restoration selects configuration rather than overwriting new implementation files with old copies.

Leave system-space headroom at installation

If you intend to keep adding software, traffic analysis or NPU experiments, leaving system-space headroom at installation makes the setup easier to extend. Our initial allocation became too small, and on October 23, 2026 we expanded p2 from 256MiB to 5GiB. Free space across the eMMC device is not automatically available to the partition that holds added software.

One eMMC device: p1 + p2 for the OS, p3 for data

The physical storage is one eMMC device, divided into three partitions: p1, p2 and p3. Functionally, p1 + p2 form the OS side and p3 holds data. Bootloader space before these partitions is omitted from the diagram.

p2 contains both the read-only OS (SquashFS) and a writable overlay for added software and configuration changes (F2FS in this installation). The full p2 capacity is therefore not all available as writable overlay space. p3 is a separate ext4 partition for logs and databases, placed immediately after p2 in this layout.

Are the OpenWrt defaults small?

In the upstream OpenWrt 25.12.5 source checked on October 23, 2026, the generic defaults are CONFIG_TARGET_KERNEL_PARTSIZE=16 and CONFIG_TARGET_ROOTFS_PARTSIZE=104, in MiB. Rockchip image generation uses these two settings. They do not allocate the whole of a large eMMC device to the OS.

Device and build settings can override those values. Our measured pre-expansion p2 was 256MiB, about 2.5 times the generic 104MiB default. It therefore already provided extra capacity compared with that small baseline, yet our added functions and update workspace eventually exceeded it. The original build-setting decision has not been traced, so we do not claim how or why 256MiB was selected.

Partition size, download size and write volume are different

An offline comparison on October 23 also examined update-image sizing. On a Mac, it kept the OS payload from an existing, uninstalled image unchanged while varying p2 allocation and zero padding. Empty space compresses well, so gzip size does not grow in proportion to partition capacity.

The gzip values exclude trailing distribution metadata. The last column includes the 16MiB p1 and represents write volume, not measured device write time. Streaming decompression also avoids expanding the entire 5GiB image in RAM at once. A full-range writer still writes the zero padding, however, so a small download alone does not establish a fast or low-write update.

This comparison establishes sizing and writer mechanics. It does not cover real-device update acceptance, F2FS initialization, configuration retention, reboot or network downtime. Choose capacity with future additions and a validated update/recovery method in mind, rather than treating RAM alone as the deciding factor.
