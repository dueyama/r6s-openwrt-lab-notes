Python → Rust

Which processing changed, how timings changed and what maintenance dependencies were removed.

Page revision: 2026-11-11 · Comparison conditions for SQL optimization and language migration

What you can explore here

When processing gets slow, it helps to find where the time goes. This experiment improved database queries first, then compared Python and Rust. The record explains both the timing results and how the router ended up with fewer software dependencies.

Evaluating SQL changes, language migration and dependency removal separately makes it easier to explain which changes helped.

Python introduction, Rust migration and dependency removal

Codex initially installed Python to implement the IDS monitoring functions. The implementation was later changed to Rust to move R6S-side processing to native code and remove the Python dependency. The migration covers deterministic IDS-log processing: parsing, deduplication, aggregation, SQLite persistence, audit snapshots, judgment history and display-data generation. This is documented separately from 115-feature extraction and NPU model inference. AI interpretation of logs was not replaced with Rust.

Keep the two comparisons separate when quoting

SQL optimization within Python measured 46.528 s → 0.596 s. The separate same-10,000-row language comparison measured Python 0.358 s versus Rust 0.216 s. These cannot be combined into one Python-to-Rust 46.5 s → 0.2 s comparison. The tables below state each workload and comparison scope.

2026-09-27
Optimized SQL access in the Python implementation: repeated per-event history queries were replaced by loading per-incident revision counts once per transaction. Results matched across 12 DB tables and 14 existing state tests passed. Algorithm and I/O changes preceded language migration.
2026-09-28
Compared parsing, deduplication, aggregation and SQLite storage for the same 10,000 Snort-log rows, with three runs per implementation, fresh databases and alternating execution order. All event/group rows matched in all three comparisons.
2026-10-06
Migrated production processing to a static AArch64 Rust helper. DB schema, byte cursor, existing judgment history and snapshot-SHA compatibility were preserved; installation checks moved to shell, ucode and native code. Python packages on the R6S were removed after native operation and dependencies were checked. Post-removal collection and DB-integrity checks succeeded.

Operational example under different conditions

After native Rust cutover, an operational collection of 8,762 records completed in 5.52 seconds. Its input and scope differ from the matching 10,000-row Python/Rust comparison above.

Reduced security-maintenance scope

The outcome includes more than execution-time and memory changes. Records dated 2026-10-06 confirm removal of 21 Python-related packages after native operation and reverse dependencies were checked, leaving zero Python packages on the R6S. The installed Python interpreter, standard library and related packages could therefore be removed from that router’s vulnerability-applicability review and update scope.

This reduces dependency components and maintenance scope. It is not a finding that using Python was itself a vulnerability. The Rust binary, dependency crates, SQLite and OS still require review and updates; Python removal alone does not establish system-wide security.

Cutover compatibility and environment checks

The final version passed 19 unit tests, 25 CLI tests, 8 deployment tests and 16 byte comparisons against the old parser. Dependencies on unavailable external commands were replaced with ucode stat handling and Rust subprocess handling with time and output limits. Cutover preserved the DB/cursor and verified history continuity with read-only checks.

Python removal refers to R6S-side processing recorded on 2026-10-06. It does not establish removal of Python from external training/management tools, full restoration, long-duration performance or a measured network interruption time.

What changed when repeated SQL queries were removed

Repeated per-event revision-history queries were replaced with per-incident counts loaded once within the transaction and updated only for new fingerprints. The rule excluding the current fingerprint was preserved. Saved evidence records matching results across 12 tables and 14 existing tests including insertion/retry behavior.

Illustrative before/after structure
# Structural illustration, not deployable production code
# Before: repeat the same history query for every event
for event in events:
    revisions = query_distinct_revisions(event.incident_id)
    record(event, revisions)

# After: load per-incident counts once for this transaction
counts = query_revision_counts_for_transaction(events)
for event in events:
    record_using_counts(event, counts)
    # Update counts only when a new fingerprint is inserted

The verified comparison: variation and output equivalence

The 10,000-row comparison above already checked matching inputs, elapsed time, CPU, memory and outputs. The saved per-run values also show the variation behind the means. These are the minima–maxima across three runs per language on September 28, 2026, not new measurements.

MetricPythonRust
CPU time0.274–0.281 s0.125–0.152 s
Peak RSS15.26–16.36 MiB8.25–12.27 MiB

Peak RSS is the maximum resident memory of each process during a run. Rust also varies across these three short runs; its 10.04MiB mean is not a constant memory requirement. All rows in the events and groups tables matched in every run, so output equivalence in this bounded scope is part of the comparison alongside speed.

The early prototype comparison is separate from the compatibility and history-preservation checks during the October 6 production migration. Possible remaining questions concern different loads/inputs, the full production pipeline and long-running memory behavior. Those gaps do not erase the existing comparison, and timings from different production event counts do not replace its speed ratio.
