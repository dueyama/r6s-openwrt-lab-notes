AI-assisted traffic-log review

How alerts are investigated, recorded and turned into human action requests.

Page revision: 2026-11-16 · AI traffic-review architecture, notifications and verification scope

What you can explore here

A growing alert list makes it harder to decide what to investigate first. This workflow uses AI to examine traffic context and earlier judgments, then identify the next useful check. Raspberry Pi 5 coordinates the work and requests GPT-6 Luna judgments through the Responses API following the October 29 evening cutover.

The central ideas are checking inputs and outputs around AI judgment, and separating alert severity from the need for human action.

Terminology
Review / event / candidate
Review here means technical examination of traffic records. Events are observations; candidates are the objects to judge, sometimes combining events.
SQLite / snapshot
SQLite stores history. A snapshot freezes the input set for one review.
Controller / batch / page
The controller manages the workflow. A batch is a group sent to AI; a page is a retrieval chunk, not a website page.
WAN / SID
WAN is the router’s external-network side. A SID identifies a Snort detection rule.
Publication / completion
Publication here updates data for the custom management UI. Completion requires verified persistence and readback for the same review.
Receipt (verification record)
A record binding the target version, evidence and result; its existence alone does not establish adoption or completion of every stage.
Formal finish (workflow acceptance)
Workflow completion after required originals, API and display evidence; distinct from fixing every software issue.
Projection / rebinding
Projection turns stored logs into aggregate/display data. Rebinding ties a review result to evidence for the corresponding configuration/version.

October 30, 2026: batch context retrieval to reduce API waiting

The API adapter was then changed to request needed context in batches. One old/new API pair using the same 48 candidates, context mapping and revised instructions fell from about 207.2 to 103.1 seconds and from 81 to 13 HTTP requests, roughly halving elapsed time. This was a single sequential comparison, not a continuous performance guarantee.

After separate quality review and deployment, a real review starting at 00:14 JST on October 30 completed 35 candidates in five batches in about 93.8 seconds. Its different input prevents using successive production durations as a speedup ratio. HTTP time includes network and service time, without isolating inference. Total input fell while uncached input rose, so lower charges are not established.

From input to verified completion

A review fixes its input, examines every candidate and records the judgments. The sequence shows where AI makes judgments and where software checks the work.

  1. Collect Snort alerts and WAN records into SQLite. Event counts and aggregated review-candidate counts are distinct.
  2. Freeze the review window, candidates and context in a snapshot. Later collection does not replace the input halfway through this review.
  3. The controller checks original pages, ordering and complete candidate coverage, then forms batches of complete candidates rather than truncating text.
  4. GPT-6 Luna reads candidates and prior judgments, checking additional history/search context when needed. It returns outcomes, reasons, uncertainty, reevaluation conditions and human questions.
  5. The controller validates response IDs, counts, states and required fields. It does not rewrite missing, duplicated or invalid answers into convenient judgments.
  6. After all responses are validated, persist only required changes. Verify result readback, DB integrity and completion for the same audit ID.
  7. The UI presents investigation state and human actionability; notification handling decides delivery. A failed review is not converted into an all-clear result.

What counts and states mean

To read the dashboard counts, distinguish observed events, review candidates, AI investigations, human requests and sent notifications. The guide below explains what each represents.

Event
An observation recorded by a detector or other source, not every traffic packet.
Review candidate
An object to judge in a review. Multiple events with the same context can contribute to one candidate.
Judgment history
A history of when, why and on what evidence an outcome was reached, and when to reconsider it.
Completion receipt
Evidence that processing and persistence/readback completed for the fixed review set, not a safety certificate for all traffic.

Severity, investigation progress and the need for human action are separate dimensions. An unknown cause need not imply immediate human action; quiet presentation also must not erase danger findings or history.

These are illustrative design examples, not household logs, actual case judgments or detector-performance test results.

Which changes cause an incident to be reconsidered

This summary follows the saved Rust implementation of incident identity and reevaluation-candidate creation. The same identity does not by itself mean the old judgment is automatically adopted.

ChangeIncident IDReevaluation candidate
Count increasesSameAn increase alone does not always trigger reevaluation. A comparison with the previous completed window must meet duration, count and rate-change conditions.
Only a port changesSameA port change alone is not a separate trigger. Individual events remain recorded, and other conditions such as frequency still apply.
Revision changes for the same SIDSameA revision differing from existing revision history creates a rule-revision reevaluation candidate.
A related alert is addedDepends on SID, peers, protocol, message, etc.A different SID forms another incident. New destinations or protocol/message changes can create separate incidents and reevaluation reasons. Related alerts are not all collapsed into a single identity.

Prior judgments remain in history. The input includes reevaluation reasons and prior judgments; AI returns keep or a new judgment, and the controller validates and appends changes. Creating a reevaluation candidate does not itself erase the old judgment or notify a person. Some informational signatures also use a source-grouping exception to the general identity key.

AI-assisted traffic-log review: initial alert noise and design revisions

The project-specific implementation is the review pipeline: collecting alerts from Snort and other sources, combining traffic context and prior judgments, and connecting AI review to persisted history, UI and notifications. GPT-6 Luna is the existing OpenAI model used for judgment; the pipeline is distinct from stock Snort functionality or a custom-trained detector.

Initial problem: rule matches, pending investigation and human requests

The initial system produced many alerts and review requests. Records dated 2026-09-25 describe numerous informational PING/UPnP alerts, an oversized review list, and changes to distinguish observation from human requests. On 2026-09-26, a stale screen also displayed historical AI-investigation totals as items requiring attention. Detected events, investigation candidates and new actionable requests needed separate meanings.

These were not all established false positives. The revisions distinguish informational rule matches, insufficient evidence, presentation problems and genuinely actionable events.

Judgment policy: investigate before escalating

Meaning of a rule match
A matching signature ID creates an investigation candidate rather than an automatic danger finding. The review checks device/destination context, frequency, time window, related logs and prior reasoning, while recording what was not observed.
Unknown versus actionable
An unknown cause alone is not a reason to request human action. Low-confidence unresolved cases remain under AI investigation or observation. Escalation is for a concrete decision/action or significant remaining suspicious evidence.
Recurrence
Recurrence, deterioration or new evidence triggers reevaluation. Repetition alone neither creates a new human notification every time nor establishes safety. Unobserved cessation or absence of harm is not asserted.
Judgment record
Store the outcome together with reasons, evidence used, uncertainty, reevaluation conditions and any human question. Preserve prior judgments/history and distinguish new events from historical handled aggregates.

UI and notification changes while retaining detection records

Observation items were collapsed, duplicate presentation was reduced, and AI investigation was separated from human action requests. Danger indicators remain visible; aggregate replacement checks that referenced records exist. Rule removal or blanket downgrading merely to reduce notification counts is not treated as an improvement.

User notifications target meaningful changes, concrete action needs or monitoring failures, with deduplication of repeated delivery and notification-history entries. Quiet operation is not a quota such as a maximum number of alerts per month. UI collapsing, judgment changes and notification suppression are separate operations.

Persistence and execution: SQLite, Pi 5 and Rust controller

2026-09-26 / 2026-10-02
Events and judgment history were persisted in SQLite, with deduplication, incremental retrieval and cursor handling. By October 2, candidates and context were fixed into one snapshot, enabling completeness checks against a stable review set despite ongoing collection. UI states distinguish running, completed, failed and unverified reviews.
2026-10-06
Review orchestration moved from the Mac to a Pi 5. The R6S retained collection, authoritative SQLite and history, decoupling routine review from the development Mac. Traffic-log review remains separate from software-vulnerability/update review.
2026-10-11
When AI also controlled retrieval and saving, a run could retrieve every page yet stop with unread content. The Rust controller now checks candidate IDs, ordering and original bytes/hashes and supplies complete small batches to AI. AI performs judgment; deterministic code controls retrieval, completeness, persistence and completion checks.

Changes are saved only after validated responses cover all candidates and the WAN review. Publication, readback and SQLite integrity use the same snapshot/audit ID. CLI exit zero or scheduled startup alone is not review success. Retrieval of every page is also distinct from proof of correct AI interpretation.
