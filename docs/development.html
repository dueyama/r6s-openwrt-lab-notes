2026-11-04：Macの開発領域を追加し、Docker共有のファイル仕様を確認

2024年のMacに、大文字と小文字を区別するAPFSの開発用ボリュームを追加しました。上限128GiB・予約容量0の設定で、128GiBを独立したディスクとして確保したわけではありません。Colima/Dockerからの共有を設定し、既存VMや保存コンテナを保ったまま、大文字小文字が異なるファイル、リンク、実行権限、fsyncとatomic rename、更新時刻とmakeの増分判定を小規模な試験で確認しました。

Mac側の新しい共有領域と、Linuxゲスト内の既存ファイルシステムの空き容量は別です。この共有試験でソース・Git・SDKを一括移行したわけでも、カーネルや全SDKのビルドを受け入れたわけでもありません。OSの構築では、単に空き容量を増やすだけでなく、ビルドが期待するファイル名・権限・更新判定を作業場所で確かめる必要がある、という実例になりました。

現用ファームウェアの再構成と、次のカーネル候補の準備

新しい領域では、現用のLinux 6.12.112と既存2修正のカーネル再構築を進め、固定した公式rootと26個のAPK、再構築したカーネルからファームウェアをオフラインで組み立てました。対応する60ファイルの内容・サイズ・ハッシュを2024側で照合しています。キャッシュを使った増分構築・再構成の結果であり、すべてを初期状態からmake worldした記録ではありません。

並行する6.12.113候補は、既存パッチ群の適用と設定生成まで進みました。保存された段階では大型コンパイルは未開始で、実機への書込みや起動受入も行っていません。再構成した現用版についても、生成物照合と実起動・全kmod互換性・復元試験は別です。以前のカーネル更新で学んだ「ビルド成功だけでは足りない」という境界を、今回も保持しています。

開発・ビルド環境：Mac / Colima / Docker

実機側の構成とは別に、Mac上の既存Colima / DockerをLinuxビルド環境として利用しました。2026-09-11の記録では、Ubuntu 24.04 arm64 コンテナーで公式OpenWrtソースからPi 3向けのビルド用ツール群、カーネル、必要なパッケージ、ファームウェア イメージをビルドしています。R6S導入後は対象機種の設定・成果物を分けて管理しました。

実機側
検査済みファームウェア / パッケージをPi 3またはR6Sへ導入し、起動・設定保持・機能を別に確認する。DockerはここではMac上のビルド基盤であり、R6Sの監視処理をコンテナー化した構成ではない。

ビルド成功、生成物のハッシュ確認、実機導入、実機での動作確認は別の検証段階です。ソースの保存やGitのコミットだけで、全世代の完全再現・復元が実証されたとは扱いません。

本実験では、公式OpenWrtのソースを基に、必要なビルド用ツール群・カーネル・選択したパッケージ・ファームウェアイメージを構築し、独自機能を組み込んだR6S向けファームウェアで運用しています。ソースとビルド環境を管理する利点は、公式の修正版リリースを待たずに、修正パッチや個別パッケージの更新を取り込む選択肢を持てることです。

先行対応するかは、問題の影響、修正の確かさ、互換性、検証結果、その後の保守負担を見て判断します。カーネルなどの共通基盤は公式の安定版に追従することを基本とし、個別の先行修正は影響範囲を確認して判断します。 保守方針と先行対応の具体例

ここでいうビルドは、選んだ構成に必要な一式を作ることです。更新時には増分ビルドも使い、毎回のクリーン全ビルドや全パッケージの総当たりを意味しません。NPU用SDKなど、別途組み込む配布物もあります。

SD保管と起動の使い分け

既存のDeco X95＋Wi-Fiメッシュへ、どうR6Sを入れたか

もともとは、TP-Link Deco X95をルーターとして使い、DecoのWi-Fiメッシュで家庭内をつないでいました。この環境へ、通信の出入口と観測を担当するR6Sを追加しました。Wi-Fiを担当するDecoは引き続き使い、ルーター機能をR6Sへ移す構成です。

R6Sには内蔵Wi-Fiがないため、R6SのLANとメインDecoをEthernetで接続します。DecoはAP（アクセスポイント）モードへ切り替えました。導入当時のnoteで「ブリッジモード」と書いたのは、この役割分担を指しています。

機能導入前切替後

DHCP・予約・DNSDecoの設定を使用R6Sへ設定を移し、DNSの窓口もR6Sへ
Wi-Fi・メッシュDecoで提供DecoをAPモードで継続利用

どう切り替えたか：9月25〜26日の記録

  1. まずDecoの下流で試す。R6SのWANを既存のDecoのLANへつなぎ、R6SのLAN側は別の試験ネットワークとして管理Macと接続。普段の回線をDecoに任せたまま、R6Sの起動・ポート対応・外部通信を確認しました。
  2. 回線側へ移す。ONUとDecoの間のEthernet配線を、ONU → R6S WAN、R6S LAN → Decoへ変更。作業記録には、Decoをルーターモードのまま残した暫定二段構成で、WANのDHCP取得と外部HTTPSを確認した段階があります。
  3. DecoをAP化し、家庭内LANの設定を引き継ぐ。本人がDecoをAPモードへ切り替え、R6Sへ従来のLANアドレス体系・DHCP配布範囲・予約設定を移しました。多数の端末がR6SからDHCPを受けることを確認し、その後、端末へ知らせるDNSもR6Sへ変更しました。
  4. 配布設定を調整する。DecoのスマートDHCPは本人が無効化。移行中に起きたR6S側のDHCP停止も修正しました。予約設定を移したことと、すべての端末が新しいリースへ更新されたことは別に確認します。
  5. 接続速度も実測する。翌9月26日にDeco側を1GbEポートから2.5GbEポートへ差し替え、R6Sとのリンクが2.5Gbps／全二重になったことを確認しました。これはポート間の接続速度で、インターネット速度や監視込みの処理性能の測定ではありません。

DNSをTailscaleとどう使い分けたか

移行時につまずいたこと：DHCP停止

旧管理アドレスを一時的に残す設定で、同じLANブリッジを指すDHCP設定を「配布しない」としたところ、dnsmasqの生成設定にブリッジ全体をDHCP対象外にする指定が入りました。不要なDHCP設定節を取り除き、配布を戻しました。アドレスの引継ぎだけでなく、生成された設定と実際の配布を確認する必要があった例です。

自分の環境で試すときの確認点

ONUなどの上位装置からの接続方式、DecoのAPモード対応、DHCPの担当、必要な予約・ポート転送などを先に整理します。AP化するとDecoのゲートウェイ向け機能は変わるため、Wi-Fiメッシュを継続できることと、従来の全機能をそのまま使えることは分けて考えます。動的IPがすべて以前と同じになるとも限りません。

ゲストWi-Fiの分離や、実際の有線／無線の接続状態は別途確認します。配線とDecoの元設定を残し、切替に問題があれば旧配線・Decoのルーターモードへ戻せるようにします。Pi 3は予備試験機だったため、旧ネットワークの復旧先はDeco側です。

DNSの工夫：通常の名前とTailscaleの名前を振り分ける

DNSは、機器名やサイト名から接続先のアドレスを調べる仕組みです。当時は、通常のサイト名に使うDNSと、Tailscale参加機器の名前を引くMagicDNSを併用する構成でした。9月25日のMacの読取り記録には、通常のDNSと、Tailscaleのドメイン専用の名前解決先の両方が確認できます。

独立実装とした理由：ソース管理と更新追従

LuCI拡張をやめた理由の一つは、ソース管理を単純にすることです。標準LuCIのソースに独自変更を重ねる方式では、LuCI本体が更新されるたびに、こちらの変更の再適用・調整・競合解消と動作確認が必要になります。標準側の変更と自作機能の変更を同じソース上で追従させる作業を減らすため、観察・運用画面を独立した管理画面へ切り出しました。

自作画面のHTML / CSS / JavaScriptとAPIを独立した単位で履歴管理し、標準LuCIの更新と自作機能の更新を分ける設計です。これはソース管理上の狙いであり、保守工数の削減率を実測した結果ではありません。OS・データAPI・標準設定との連携は引き続き確認します。

LuCI拡張と独自管理画面は別の実装段階です。独自画面への切替日そのものはここでは特定せず、確認できた記録の日付を付しています。管理URLや端末識別情報は掲載せず、下の画面例には保存済みの実画面を使っています。

2026-10-27：WAN集計を広げ、同じ観測時間で比較する

従来の「WANからルーター自身へ届き、拒否された通信」の集計を残し、OpenWrtの標準ファイアウォールfw4で終端のdrop／rejectとなる、確認済みの追加範囲を観測するモードを加えました。通過・遮断の方針を変更する機能ではなく、既存の判断をカウンターで観測する機能です。数える単位はパケットで、接続数や攻撃件数ではありません。

追加範囲の記録は10月27日に開始し、過去へさかのぼって埋めていません。合計は、従来範囲と追加範囲の両方に有効な記録がある同じ時間だけで計算します。そのため、拡張モードの合計が、長い履歴を含む従来モードより小さく見える場合があります。比較するときは数だけでなく、対象時間もそろえます。

保存された実測例：同じ時間で足す

10月27日の導入確認では、従来範囲は3,540秒分で22パケットでした。一方、追加開始後の共通180秒は従来11＋追加0＝合計11パケットです。対象時間が違うため、22に追加分を足して比較しません。これは担当の受入記録に保存された一時点の値で、下のスクリーンショットとは別の取得時点です。

時系列では従来範囲を緑、追加分を橙の面、共通範囲の合計上端を橙の破線で表します。記録開始前・欠測・一部だけの区間は0に置き換えず、実測0と区別します。Snortの系列は別の右軸です。PC・狭幅画面と複数期間のAPIを照合し、切替で元の履歴とSnort系列が変わらないことを確認しました。

上流で届かなかった通信、ドライバ以前、通過した通信など、見えない範囲は残ります。保存容量などで追加範囲の記録が止まれば、従来記録を継続しつつ追加分を欠測と扱います。永続化の設定は確認しましたが、今回の更新で実際の再起動・再読込み試験はしていません。パケット処理性能の向上を実測した結果でもありません。

次の試行：暗号化通信の用途を推定できるか（2026-10-23）

Kitsuneが「普段と違う通信」を調べるのに対し、この試行の目的は「通話活動・クラウド通信・その他」という用途の推定です。将来の優先制御を考える前段階として、復号せずに使える情報でどこまで区別できるかを比較しました。2024年のMacで公開データを使ったオフライン実験で、R6Sへの導入やNPU動作、自動QoSの有効化は行っていません。

初回の5用途比較に続き、音声通話・クラウド・ブラウザ等の公開記録を追加し、574 PCAP・13,157接続・549収録グループで3用途を比較。同じ収録を学習・校正・評価にまたがせず、未学習のアプリと地域も別に留保しました。接続開始後0.25秒・1秒・3秒、最大64パケットという条件です。機械学習にはサイズ・方向・間隔等を使い、IPアドレス、ポート、SNI、通信本文は入力しません。nDPIは復号せずに見える接続開始時の情報も利用し、用途を確定できない接続を統計モデルまたは小型ニューラルネットワーク（NN）で補いました。

1秒時点の通常評価1,848接続では、nDPI＋forest（複数の決定木を組み合わせる統計モデル）の全体正答率80.63%、nDPI＋NNは81.33%でした。ただし、収録と用途を均等に重くする評価では83.88%対81.75%で統計側が上回り、未学習地域ではNN側の誤通話判定が増えました。保留は正答に含めていません。通話には制御接続、クラウドには制御通信も含むため、音声パケットやファイル転送そのものの検出率とは異なります。NNの総合的な優位や家庭での実用精度を確認した結果ではありません。

選択されたNNのMac上での標準化＋推論は中央値35.06µs、選択forestは963.73µsでした。一方で、もっと速い浅い木・線形モデルもあり、NNが統計方式すべてより速いわけではありません。収集・特徴抽出・nDPIはこの計時に含めていません。用途の保留設計と、端末・地域・アプリが変わった場合の検証を先に改善する、という段階です。
