AIによる通信ログ監査

警告をどう調べ、履歴を残し、人への対応依頼につなぐか。

本文更新：2026-11-16 · 通信ログAI監査の構成・通知・確認範囲

このページで紹介すること

警告が増えると、何から調べればよいかが分かりにくくなります。そこで、過去の判断や通信の文脈をAIと一緒に調べ、次の確認につなげる仕組みを作りました。Raspberry Pi 5が処理を進め、10月29日夜からResponses APIを通じてGPT-6 Lunaへ判断を依頼します。

AIに判断を依頼する前後をプログラムで確かめること、警告の強さと人の対応要否を分けることが、中心となる工夫です。

保存された一回の監査を読む · AIの前後で行う処理

用語の補足
監査 / event / 候補
ここでの監査は通信記録の技術的な確認。eventは個々の観測、候補は複数の観測を整理した判断対象。
SQLite / snapshot
SQLiteは履歴を保存するデータベース。snapshotは一回の監査で読む入力を固定した記録。
controller / batch / データページ
controllerは進行を管理するプログラム。batchはAIへ一度に渡す候補の束、データページは分割して取得するデータの単位。Webサイトのページとは別。
WAN / SID
WANはルーターの外部ネットワーク側。SIDはSnortの検知ルールを識別する番号。
結果反映 / 完了
結果反映は独自管理画面に表示するデータの更新。完了は同じ監査の保存・読戻しが確認できた状態。
receipt（確認記録）
対象の版・根拠・結果を結び付けて残す記録。存在だけで実機導入や全工程の完了を示すものではない。
正式finish（工程の受入完了）
必要な原本・API・画面証跡などをそろえた工程上の完了。ソフトの全問題を直したという意味ではない。
投影 / 再結合
投影は保存ログを集計・表示用データへ整形すること。再結合は監査結果を対応する構成・版の根拠へ結び直すこと。

2026-10-29：通常監査をCodex CLIからResponses APIへ

10月29日夜、Pi 5の通常の通信ログ監査を、Codex CLI / app-server経由からOpenAI Responses APIを直接呼ぶ方式へ切り替えました。判断モデルはGPT-6 Luna（gpt-6-luna）、推論設定はlowを維持しています。Macで設計・開発・検証を進めるCodexアプリの役割は続き、定期監査のモデル呼出し口を変更したものです。

Rust側が対象の固定、候補ID・文脈の照合、回答検証、保存と完了を管理する構造は維持しました。切替前の比較は48候補・6バッチで、欠落・重複や未取得文脈がないことを確認し、判断の差も審査。その後、実入力43候補・6バッチの一回の監査を完了し、結果保存と整合性まで受け入れています。一組の比較を、将来すべての判断の正しさへ広げません。

最初のAPI経路は、同じ入力の記録で約237秒に対しCodex参考値は約86秒と、むしろ遅くなりました。この比較と、その後のAPI内部の最適化比較は別です。APIへ移っただけで高速化したとは書かず、呼出し回数と待ち時間を分けて調べました。

2026-10-30：文脈取得をまとめ、API呼出しの待ちを減らす

続いて、必要な文脈をまとめて要求できるようAPIアダプターを変更しました。48候補・同じ文脈対応表・同じ改訂指示文を使うAPI旧版／新版の一組では、約207.2秒から103.1秒へ、HTTP要求は81回から13回へ減少しました。所要時間は約50%短縮しましたが、単発の順次比較であり、常時の速度保証ではありません。

別に品質を確認してから新版を導入し、10月30日00:14開始の実監査では35候補・5バッチを約93.8秒で完了しました。この実監査は入力が違うため、前後の実運用時間をそのまま高速化率には使いません。HTTP時間には通信とサービス側の時間が含まれ、推論だけの時間には分解していません。総入力トークンは減ってもキャッシュされない入力は増えたため、料金が安くなったとの結論も出していません。

入力から完了までの処理

一回の監査では、読む対象を決め、候補を漏れなく調べ、判断を履歴へ残します。AIが判断する部分と、プログラムで確認する部分を順に示します。

  1. Snort警告やWAN記録を収集し、SQLiteへ保存する。イベント件数と集約された監査候補の件数は別に扱う。
  2. 対象範囲・候補・関連文脈を監査用の記録として固定する。後から収集が進んでも、この監査の入力を途中で入れ替えない。
  3. 制御プログラムが元データの各ページの対応・順序・全候補を照合し、完全な候補単位のバッチへ分割する。途中の文字列切断で情報を落とさない。
  4. GPT-6 Lunaが候補と既存判断を読み、必要な履歴・検索の追加文脈を照合する。結論、理由、不確実性、再評価条件、人への質問を返す。
  5. 制御プログラムが回答のID・件数・状態・必要項目を検証する。欠落・重複・不正回答を、都合のよい判断に書き換えて通さない。
  6. 全件の回答が検証された後に、必要な変更だけを履歴へ保存する。反映結果と読戻し、DB整合性、同じ監査IDの完了を確認する。
  7. 画面は調査状態と人の対応要否を表示し、通知は通知処理が判定する。監査失敗を「問題なし」へ変換しない。

何をAIへ渡し、どこまで任せるのか

Pi 5で処理を動かすことと、推論が家庭内だけで完結することは別です。ここで使うGPT-6 Lunaの判断は外部サービスです。10月29日夜から、接続口はCodex CLI経由からResponses APIへ移っています。サイトの掲載情報と、実際のAI入力が匿名化されているかどうかは別に確認します。

数えているものと状態の意味

画面の数字を読むときは、観測したイベント、整理した候補、AIの調査、人への依頼、送信済み通知を分けると理解しやすくなります。以下は、それぞれが何を表すかの整理です。

イベント
検知器等が記録した個々の観測。すべての通信パケットを意味しない。
監査候補
監査で判断する対象。同じ文脈の複数イベントが一つの候補に集約される場合がある。
判断履歴
いつ、どの根拠で、何を判断し、どの条件で見直すかという記録。現在値だけではない。
監査完了記録
固定した対象の工程が終わり、保存・読戻し等が確認された記録。全通信の安全証明ではない。

表示上の重大度、調査の進み具合、人が対応すべきかは別の観点です。原因がまだ不明でも、直ちに人の操作が必要とは限りません。一方、画面を静かにするために危険な判断や履歴を消す設計でもありません。

判断の違いを読むための模式例

以下は設計を説明する模式例です。家庭の実ログ・実際の判定事例ではなく、検知性能を評価する試験結果でもありません。

情報系ルールへの単発一致
通信の目的と文脈、既存判断、継続性を調べる。具体的な危険根拠が足りなければ、条件付きで記録・経過観察とする。安全確定とはしない。
同じ候補の再出現
前回から量・相手・挙動・根拠が変わったかを比較する。再発だけで毎回通知せず、重要な変化があれば再判断する。
監査が途中で失敗
未完了・監視失敗として区別する。直前の完了結果を今回の結果として使わず、AIが答えなかった候補を正常扱いにしない。

同じ候補でも、どの変化で見直すか

保存済みRust実装の候補IDと、再評価候補の作成処理に基づく整理です。「同じID」と「以前の判断をそのまま採用する」は別の条件です。

変化案件ID再評価候補の作成
件数だけ増える同じ増加だけでは常に再判断しない。前回の完了した観測窓と比較し、観測時間・件数・増加率の条件を満たすと再評価候補を作る。
ポートだけ変わる同じポート変更そのものは独立した再評価理由にしない。個々のイベントは保持し、頻度等の別条件は引き続き評価する。
同じSIDで改訂番号が変わる同じ既存の改訂履歴と異なる改訂を観測すると、ルール改訂を理由に再評価候補を作る。
関連する別の警告が加わるSID・相手・通信種別・警告文等に依存別SIDは別の案件。送信先の追加や通信種別・警告文の変化は条件により別案件と再評価理由を作る。単に「関連」とされた全警告を一つへ統合するわけではない。

前回判断は履歴として残ります。再評価理由と既存判断を入力に含め、AIは維持（keep）または新しい判断を回答し、制御プログラムが検証して変更分を追記します。再評価候補の作成は、以前の判断の消去や、人への通知を直接意味しません。なお、集約キーには一部の情報系ルールで送信元をまとめる例外もあります。

回答が一件足りなかったら

以下は欠落時の処理仕様を説明する例です。実行記録ではありません。AIが判断を返し、Rust製の制御プログラムが対象との対応・欠落・保存・完了を管理します。

段階合成例の処理
固定した入力候補A、Bの2件。
不完全な回答Aの判断だけが返る。Bは欠落。
全件照合Bがないため完了と認めず、部分回答を全件成功として保存しない。
限定した再試行同じバッチを1回まで再試行する。認証・権限・明示拒否では行わない。
再試行も欠落今回の監査失敗を記録。Bを正常扱いにせず、前回の完了結果と今回の失敗を分けて表示する。

判断基準の変更：AIが先に調査する

ルール一致の位置付け
SID一致だけで危険を確定せず、AIが調べる候補とする。端末・通信先・頻度・時間範囲・関連ログ・過去判断の根拠を確認し、何が観測されていないかも記録する。
不明と人対応の分離
原因不明であることだけを人への依頼理由にしない。低確度の未解決はAI調査中または経過観察として残し、具体的な判断・操作が必要な場合や重要な不審根拠が残る場合に人へ依頼する。
再発の扱い
再発・悪化・新しい根拠があればAIが再評価する。単なる再発で毎回人へ通知せず、繰り返すというだけで安全とも認定しない。観測していない停止や実害の不在を断定しない。
判断記録
結論だけでなく、理由、使用した根拠、不確実性、次に見直す条件、人への質問を保存する。既存の判断と履歴を継承し、新しいイベントを過去の対応済み集計と混同しない。

表示・通知の改良と、検知記録の保持

経過観察を折りたたみ、重複表示を整理し、AI調査中と人への対応依頼を別に表示した。危険表示は残し、集計に置き換える場合も参照先が実在することを検査する。単に通知件数を減らすためのルール削除や、全件の一括降格を改良としない。

利用者への通知は、意味のある変化、具体的な対応、監視不能などを対象にし、同じ通知の再送や通知履歴への重複登録を抑える。静かに運用する方針は、警告を月何件以下にするような件数制限ではありません。画面の折りたたみ、判断の変更、外部通知の抑制は別の処理です。
