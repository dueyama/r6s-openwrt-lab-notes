What you can explore here

This experiment asks whether the R6S NPU can turn departures from usual traffic patterns into useful numerical scores. Traffic statistics feed a trained model, and a history view makes changes visible. Start with the processing flow, then explore feature design and numerical comparisons with the CPU.

October 30 added split capture; October 31 verified a natural notification through displayed AI analysis, separately from physical phone delivery or continuous reliability. Detection and false-alarm tests on public Mirai records and synthetic traffic are documented on the Kitsune page. Terminology
Passive observation / acceptance
Passive observation records and displays scores. Acceptance means checking stated conditions before using the result for that purpose.
Features / Kitsune
Features numerically describe traffic, such as sizes and timing. Kitsune evaluates departures using traffic statistics.
Training / inference / frozen model
Training fits parameters; inference uses them. A frozen model does not keep retraining during observation.
FM / AD
FM learns feature grouping; AD subsequently trains the anomaly detector.
CPU64 / FP16
CPU64 denotes a 64-bit floating-point reference. FP16 is a 16-bit floating-point format, requiring separate numerical checks.
MI / H / HHjit / HH / HpHp
Feature-group labels for device identity, hosts, timing, host pairs and socket/port pairs.
Driver / runtime / SDK
The driver connects the OS to the NPU; the runtime executes models; the SDK provides development/conversion tools.
IOMMU / device tree
An IOMMU manages device memory accesses. A device tree describes hardware to Linux.
LUT / sigmoid / NHWC
A LUT is a lookup table; sigmoid is a numerical activation function; NHWC describes input-array layout.
Receipt (verification record)
A record binding the target version, evidence and result; its existence alone does not establish adoption or completion of every stage.
Formal finish (workflow acceptance)
Workflow completion after required originals, API and display evidence; distinct from fixing every software issue.
Projection / rebinding
Projection turns stored logs into aggregate/display data. Rebinding ties a review result to evidence for the corresponding configuration/version.

The finalized D168 minute bin for 18:18–18:19 JST on November 15 was the first observed strict >0.5 bin under the same input policy. This does not mean all 577 were high; retained aggregates cannot recover the individual high-score count or exact event second.

The following minute’s maximum was about 0.02843; no further finalized >0.5 bin appeared through 18:31. Model/input-policy identity checks passed, with zero totals in the nine monitored counters for that source generation and no quality hold. Nearby whole-CPU 60-second averages were about 3.1–3.2%. These do not rule out instantaneous/per-core peaks or establish all-input latency.

The event occurred about two hours after power recovery, not immediately at startup. Twenty-six minute slots around the reboot were unobserved; cross-generation loss increments remain unknown. Those are unobserved time slots, not a count of missing individual scores. Missing values were not filled with zero, and counters were not subtracted across reboot to claim zero loss.

The supported conclusion is one retained minute containing an unusually high score. Aggregates alone cannot identify the device, app or peer, or distinguish rare legitimate traffic from an attack. They do not establish detection or false-positive rates. Earlier zero-exceedance records remain valid as dated observations.

What one natural suppression event established

One saved event was about 811 ms old; explicit waiting occupied about 732 ms of the roughly 734-ms instrumented interval, while feature computation in that interval took about 47 µs. Roughly 77 ms was uninstrumented and cannot be assigned to driver or computation. This does not explain all 1,125 earlier-generation suppressions. The repair therefore addressed waiting rather than assuming CPU shortage or slow NPU computation alone.

r6s-c72-live r16/r6s-parallel-live r14 introduced processing-time commitment when later packets do not arrive. This changes how arrivals after commitment are treated, so it has a separate input policy and history/observation baseline. The 115-feature mathematics and model weights did not change. Current time and freshness are rechecked after feature calculation, retaining refusal of stale output.

Cutover initially failed pre-start qualification with binding_unverified because required new history directories were absent, not because an NPU driver failed after inference began. Waiting and suppressed output: separate CPU cost from missing diagnostics

Lighter feature computation did not eliminate stale-output suppression. In one retained window, the item age was about 810.54 ms; of about 795.50 ms covered by diagnostics, 793.98 ms (99.8%) was explicit waiting. The thread used about 2.68 ms CPU, and the feature-computation interval lasted about 0.090 ms. This window does not mean feature computation consumed about 800 ms.

When ordered inputs remain pending and traffic becomes quiet, a path can wait for a newer input timestamp before releasing the tail. The retained window is consistent with this quiet-tail mechanism, not proof of every suppression’s cause. A separate diagnostic defect was identified: repeated events on the same generation/path can increase counts without revising retained detail, so the writer does not publish a new context. Later quiet records cannot reconstruct the exact branch or timing of every past event.

Stale-output suppression counts are neither NPU driver failures nor ordinary household packets blocked by the router. A bounded latest-suppression diagnostic candidate passed source review but remains unsigned and uninstalled. It is a diagnostic improvement candidate, not a deployed quiet-tail repair or a resolution of the waiting meter.

The speed evidence has separate limits. A roughly 14-second simultaneous transfer measured about 192.4 Mbps down and 215.5 Mbps up, but retained records did not independently bind that measurement path to R6S capture; it does not qualify cleanup4 capacity or improvement over cleanup16. A separate download attempt failed with HTTP 403 and zero received bytes, producing no valid speed value. A failed measurement is not a successful high-load test.

Feature redesign and independent-reference validation

Kitsune learns patterns from traffic statistics and assigns anomaly scores to departures from those patterns. This experiment implements calculations against the paper. A feature is one numerical input describing traffic; 115 is the input count. A and B name project training generations; B was trained afresh on 24 hours of input. The Python mathematical reference is a development-side verification tool, separate from the R6S monitoring path migrated to Rust.

In the old extractor, larger state capacity and CPU work sharing did not resolve growing costs from scanning historical peers. The experiment was stopped for redesign on 2026-10-15. A 115-feature implementation was rebuilt against the paper’s equations, feature structure and state-cleanup guidance rather than agreement with the old implementation.

The specification comprises MI15 / H15 / HHjit15 / HH35 / HpHp35, totaling 115 columns. Metadata collection, CPU feature extraction and NPU inference are separate processes, so downstream stopping or replay does not require stopping collection. CPU, storage and kernel resources remain shared; process separation does not eliminate resource contention.

An independent Python mathematical reference and hand calculations were compared with production C++ across nine fixtures and 1,291 inputs. Excluding one rejected timestamp case, 127,420 values gave a maximum absolute difference of 2.91038e−11 on both Mac and real R6S. Accelerated replay of seven-day-equivalent synthetic input is distinct from seven days of continuous operation.

The original Kitsune authors’ public Python implementation intentionally uses 100 features; column count alone is not proof of an implementation error. Finite 115-feature agreement does not establish training quality, sustained full-pipeline throughput, NPU precision or attack-detection performance.

What the 115 columns describe

GroupAggregation keyStatisticsColumns
MISource MAC + source IP, including address familyPacket length: Weight, mean, standard deviation3 × 5 = 15

HHjitDirected source-IP → destination-IP pairInterarrival time in that direction: Weight, mean, standard deviation3 × 5 = 15

Every group uses five decay rates, λ = 5, 3, 1, 0.1, 0.01. Weights decay by 2^(−λΔt) for elapsed seconds Δt, giving half-lives of 0.2, about 0.333, 1, 10 and 100 seconds. This is not a fixed window that discards old inputs all at once.

For one TCP packet from A to B, update A’s MAC/IP group, A’s host statistics, A→B timing, the A↔B IP pair and the TCP endpoint pair with its ports. A reply updates the opposite side of the bidirectional pairs. Non-TCP/UDP input uses zeros for the 35 HpHp columns.

These definitions belong to the paper-based 115-feature implementation and its independent reference. Column order, initialization, timestamp regression and lifecycle boundaries are fixed separately. Inputs are not mixed with the older 100-feature model.
