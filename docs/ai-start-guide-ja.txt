「私のラズパイでできる？」から始める

手持ちのRaspberry Pi、Mac、Linux機などから、できる部分を選んで始めましょう。このガイドは、AIに環境を調べてもらい、小さく作り、確かめ、続けるための手引きです。R6S・Pi 5・2台のMacを全部そろえる必要はありません。

AI支援を前提とした「概念配布」

このサイトでいう「概念配布」は、目的・設計理由・部品の役割・入出力・確認例を渡し、それをもとに読者とAIが実装する方法を指します。ここでの呼び方であり、既存の標準規格を意味しません。説明を読んだAIが何でも再現できる、という主張でもありません。

 | 共有するもの | 各環境で決めるもの

 | 何を観測し、何を数えるかという意味 | 機種、OS、接続口、観測できる範囲

 | データ形式・計算・失敗時の状態・確認例 | 実装言語、画面、保存先、実行頻度

 | 変更の理由と検証結果の残し方 | 採用する版、必要な機能、運用方法

完成ソフトを同じ形で配る方法とは、再現する単位が異なります。画面やコードが違っても、共通仕様に対する動作は比較できます。一方、この入門仕様を満たしても、独自管理画面・AI監査・NPU実験の全体と同等になったことにはなりません。

すべてのソースをGitHubへ公開することは前提にしません。必要な設計情報と確認用データをここで共有し、厳密な版が必要なドライバ等は既存の公開コードへつなぎます。利用するOSSやSDKのライセンス・再配布条件は、それぞれ別に確認します。



機材の違いを、最初に計画へ反映する

AIと進める四つの段階

- 調べる：機種・OS・用途・接続位置を確認する。

- 選ぶ：できることと条件を説明し、最初の一つを本人が選ぶ。

- 作って確かめる：合成データ → 実機の読取り → 必要な拡張。

- 残して続ける：採用した版・判断・結果を手元に記録する。

- 機種・メモリ・CPUアーキテクチャ、OS／カーネル、空き容量、保存媒体、常時稼働や既存サービスの有無を調べる。機種名だけで可否を決めない。

- どの機器にAIが接続できるか確認する。読取り権限がなければ必要な項目だけ本人に尋ね、未確認を推測で埋めない。

- 通常のLAN端末の接続口で読めるのは、その接続口の値です。家庭内の全通信が自動で見えるわけではありません。ルーター通過、ミラーポート等の観測位置と、二重計上の可能性を別に確認します。

- ソフトを選ぶ際は、その時点の公式資料で対応OS・機種・版を確認する。この実験の日付付き構成を、現在の推奨版として固定しない。

実験や拡張をするなら、最初に領域サイズを検討する

合成データで小さく試す段階から、大きな領域が必須なわけではありません。一方、追加ソフト・通信解析・NPUなどへ広げたい場合は、OSを導入する前に、将来の追加分と更新作業に使う空きを見込んで、システム領域を大きめに取る案をAIと検討してください。

保存媒体全体の空きだけでなく、OS・追加ソフトを書き込む領域の空きと、ログ・DBの保存先を分けて見積もります。既存環境を使う場合は、まず現在の領域構成を調べ、今のままで足りるかを計画します。基本機能だけなら小さな構成で足りる場合もあります。

本実験ではp2を256MiBから5GiBへ拡張し、データの退避・復元と起動確認が必要になりました。5GiBは今回の選択であり、手持ちの機材にも同じ領域構成や容量が必要とは限りません。

領域の図・初期容量の考え方・拡張結果を読む → [https://dueyama.github.io/r6s-openwrt-lab-notes/operations.html#storage-sizing]

復元時は、ログと「どこまで読んだか」もセットで確認する

領域を広げるためにデータを復元した2026年10月23日、Snortのログ収集が一時停止しました。ログの内容は戻っていても、ファイルの識別番号（inode）が変わり、収集処理が覚えていた「どのファイルを、どこまで読んだか」と一致しなくなったためです。データ消失と決めつけず、不一致を検知して止まった事例です。

- 復元前：ログ、DB、処理位置（cursor/checkpoint）を、整合した組合せとして保存します。使っているソフトの版と、どのログ世代まで処理したかも記録します。

- 復元後：ファイルがあることだけでなく、保存元との内容一致と、処理済み範囲が一意に対応するかを確かめます。名前・更新日時・inodeだけで同じログと判断しません。

- 不一致なら調べるまで収集を進めず、以前の履歴と処理位置を残します。識別チェックを外す、位置を消す、先頭や末尾へ飛ばす、といった対処は重複や読み飛ばしにつながるため、自動で実行させません。

今回の担当は、保存元とログの内容、処理済み範囲の一致を確かめ、位置を保ったまま識別だけを一回移行しました。その後、通常の差分収集、DBとの整合、管理画面まで確認して復旧しています。これは今回の版と状態で受け入れた対応で、どの環境でも同じ操作を行う指示ではありません。AIには、復元前後の照合方法と収集再開の確認項目を、計画に含めてもらってください。

この本番ログの処理位置は、下の入門仕様で扱う速度カウンターのresetとは別です。入門例の「基準を取り直す」を、監査ログの処理位置の初期化へ適用しないでください。

ビルド成功の次に、互換性と復旧経路を確かめる

ビルドが通ったのは、成果物を生成できた段階です。今の機器で起動・通信できることや、失敗しても戻せることは別に確かめます。2026年10月29日のR6Sカーネル修正では、この確認が作業の大きな部分を占めました。

- 互換性：何と組み合わせて動くか — 機種名や版番号だけでなく、実際の設定、カーネルABI、既存モジュール・ドライバー、必要なサービスを照合します。生成した成果物と実行中の実体はハッシュやBuild ID等で対応づけます。同じ版番号でも、修正内容が同じとは限りません。

- 復旧：何を、どこへ、どう戻すか — 現用版に対応する起動内容・設定・データを保全します。バックアップの受領やハッシュ一致だけで復元可能とはせず、救援媒体の実起動、通常経路が使えなくても届く管理接続、復旧物を渡せること、対象領域と手順を確かめます。実復元まで試したかも区別して記録します。

- 適用後：書込み・有効化・機能復帰を分ける — 書込みが完了しても、再起動前は旧カーネルが動いている場合があります。新しい実体での起動後に通信・DNS・データ・必要な処理を確認します。今回のNPUは当初、手動のドライバー読込みで復帰しました。その後、起動順序を修正し、同日午後の通常再起動で手動操作なしの採点再開まで確認しています。手動復帰と自動復帰を別々に確かめた例です。

AIには、適用前に確かめること、適用後に確かめること、まだ未確認のことを分けて計画してもらいます。これらの条件が揃うまで変更を保留し、初めのカウンター表示実験にカーネル変更を必須にしません。

今回の判断・互換性検証・救援SD・起動確認の詳細 → [https://dueyama.github.io/r6s-openwrt-lab-notes/operations.html#kernel-backport-20261029]

小さな共通仕様：受信・送信カウンター

最初に実装する仕様は interface-counter-v1 です。これはこの導入ガイド用の新しい入門仕様であり、稼働中の独自監査システムのAPIではありません。

- 入力は同じ接続口の previous と current。各点は elapsed_ms（単調増加する経過ミリ秒）、rx_bytes、tx_bytes（非負の整数の累積バイト数）。nullは未取得。接続口の変更時は前の点を引き継がない。

- 判定順：currentがnullならunavailable。存在する点の項目型・有限値・非負整数を検査し、不正ならinvalid。previousがnullならwarming_up。時間差が0以下ならinvalid。受信または送信カウンターが減ったらreset。それ以外はok。

- okの場合だけ、（現在の累積値 − 前の累積値）÷（経過ミリ秒差 ÷ 1000）で方向ごとにbytes/sを計算する。ビット毎秒とは区別し、内部値を丸めず表示時に丸める。

- ok以外の速度は両方向ともnull。取得失敗・reset・invalidを0や「安全」と表示しない。最初の値、取得失敗後の再開、reset後は基準を取り直し、失敗をまたいだ平均で埋めない。invalidは破棄して基準もクリアする。

- 実機の収集周期は本人が選び、予定した取得時刻を過ぎた表示は「更新待ち／古い値」と分かるようにする。累積整数の精度を保てない実装は、黙って丸めず対応範囲を明示する。

 | 合成ケース | 期待する状態 | 受信 / 送信 bytes/s

 | normal | ok | 800 / 400

 | idle | ok | 0 / 0

 | first_sample | warming_up | null / null

 | collection_failed | unavailable | null / null

 | counter_reset | reset | null / null

 | zero_interval | invalid | null / null

 | negative_counter | invalid | null / null

JSONには入力と期待結果の7組と、連続取得の2組を同梱しています。AIが作った実装で全件を照合し、「失敗 → 再開」と「reset → 次の正常取得」の連続動作も確認してください。合格はこの計算・状態表示の範囲に限り、検知性能やセキュリティ全体の保証にはなりません。
